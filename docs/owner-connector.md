# Owner connector protocol

Protocol reference for the SDK owner-connector client. Local owner authentication,
persistence and lifecycle checks remain host responsibilities. See [release status](status.md).

## Selected transport

Accept MC-015's MERX-initiated, fixed-endpoint mTLS material exchange, with an
explicit `owner-connector` certificate role. This replaces AC-017's browser relay
of signed artifacts. A draft.9 resource certificate has no implicit connector
permission. Registration, allowed MERX origin and ATUM owner origin are fixed
server configuration; browsers supply none of them.

MERX opens the registered ATUM owner page from a user gesture in a new unnamed
popup. MERX uses `same-origin-allow-popups`; ATUM's opt-in popup uses `unsafe-none`.
Both retain strict CSP, frame prohibition and SameSite=Strict cookies. At the
original proposal snapshot, the opt-in hosts emitted no COOP. The implemented
ATUM connector host now emits `unsafe-none`; the MERX opener contract remains
`same-origin-allow-popups`. Production headers/RP are untouched. Test two genuinely
different HTTPS sites with the actual fixed ATUM RP and virtual authenticator.

Browser messages contain only pairing handles, flow/channel IDs and status hints.
Each window calls its own session/CSRF APIs. No passwords, owner session IDs,
global subject, authorization IDs or signed binding material cross origins.
Server reads, never browser success messages, establish state.

## Identity, caps and recovery

`flow_id` is a random canonical UUIDv4 generated by MERX and permanently unique
within its complete registered context. `channel_id`, offer and return handles
are independent canonical base64url encodings of 32 random bytes. Each host stores
its original local session/credential or account revision and immutable context.
Offer/return handles are stored as domain-separated SHA-256 digests, never logged.

One original flow lifetime is at most 300 seconds, shortened by both original
sessions and all later signed caps. Do not add a separately renewing 60-second
lease or channel epochs. Handles expire at the same original flow cap. No session
replacement may mutate an old flow. A live same-owner replacement session can
read history and start a fresh exact compensation action on the original flow
after a verified expiry-fence outcome. It cannot adopt the original bind operation.

Open/claim deliver a new handle once. If that response is lost before the handle
is learned, an authenticated read reveals committed state but cannot recreate
the handle. A new empty flow can then be started explicitly; no binding exists
yet. A lost pair response is different: read the committed pair, never reissue
handles or repeat the claim with another session. Pairing order is MERX saved
intent → ATUM atomic consume/pair → MERX saved paired result, with no transaction
held over HTTPS. MERX uses scoped identity only after its own paired commit.

Persist reverse uniqueness of `(full context, request_id)` and `(full context,
binding_id, binding_version)` to one original bind flow, excluding flow/session/
subject from those uniqueness keys. Preserve those associations after expiry,
cancellation and retirement. Terminal reconciliation and compensation refer to
this original flow; there is no second recovery pairing or reverse-association
transfer.

## Exact service surface

New opt-in ATUM connector listener, separate from browser APIs and draft.9 routes.
All paths below are POST, strict duplicate-free JSON, exact Content-Length and
Host, direct mTLS peer identity; no Cookie, Authorization, forwarded identity,
Origin, query, redirects, CORS or dynamic URL. Use the accepted raw framing and
bounded worker/shutdown machinery, with explicit parameters and unchanged old
defaults. Request/response ≤98,304/131,072 bytes, 5-second I/O deadline, ≤64 open
connections and ≤16 running store calls; timeout retains a slot until work ends.
The new public Node client follows the same bounds and never retries mutations.

| Path after `/v1/owner-connector/` | Exact request object | Effect |
| --- | --- | --- |
| `open` | `{flow_id, channel_id, expires_at_ms}` | First open saves immutable bind intent and returns one offer. Same-ID different intent conflicts. |
| `pair` | `{flow_id, return_handle}` | Consumes the return handle for this exact original context/session pair. Exact committed retry returns the original pair without renewing caps. |
| `reservation` | `{flow_id, reservation}` | verify real resource reservation/context/scoped identity, claim permanent reverse associations and save exact bytes once. |
| `confirmation` | `{flow_id, resource_confirmation}` | verify against its exact saved statement, save once. Activation verifies again under original caps. |
| `outcome` | `{flow_id, outcome}` | Verify AC-017 signed terminal fact for the original request/receipt; store once and update readiness. Post-expiry intake is allowed on the original paired flow. |
| `read` | `{flow_id}` | Read only this authenticated resource's flow and allowed material, including historical terminal facts. No enumeration. |

Every successful response has exact shape `{flow_id, state, expires_at_ms, context, scoped_subject, offer_handle, material}`.
`context` is the existing six-field fixed context. `scoped_subject` is null before
pairing. `offer_handle` is non-null only on the first successful `open` response.
`material` is exactly `{reservation, statement, resource_confirmation,
activation_receipt, outcome}`, each null until that phase permits disclosure;
statement is the original canonical JSON string produced by the existing fixed
statement encoder; other non-null values are exact JWS. MERX passes that original
string to its existing attach method. Do not reconstruct it with unconstrained
`JSON.stringify` or change the bytes when recovering it.
No owner operation/authorization/global-subject/session identifiers are disclosed.

Persisted state is one of `offered`, `claimed`, `paired`, `reserved`, `prepared`,
`confirmed`, `awaiting_resource`, `ready`, `cancelled`, `retired`. Response may
project `expired` for a nonterminal flow without changing its saved phase or
erasing material. `cancelled` describes the verified
`never_activated_fenced` resource outcome;
`retired` additionally requires actual ATUM compensation.

`open` and `read` may return an unpaired flow; its scoped identity and every
material field are null. Read of a claimed flow shows phase and original caps
only. Other transitions require their stated phase. After pairing, material belongs to the pinned resource
and remains retrievable after owner logout/expiry; this is history and cannot
authorize a new owner action. New stage-reservation/confirmation mutations require
the original live ATUM session and flow cap. Outcome intake is a terminal-fact
operation and may complete after that cap; it cannot activate either database.

Safe errors use `{error:{code}}`: invalid_request400, invalid_proof401,
unauthorized_resource403, not_found404, conflict/already_consumed409, expired410,
temporarily_unavailable503. A lost/late response is unknown and recovered by read.
Public client validates exact response schema and original context/flow, returns
immutable copied data, and exposes explicit `close()`; no environment fallback.

## Same-origin owner wrappers

Extend the existing ATUM host only when a matching connector service is explicitly
provided. All following POST bodies are exact; cookies/Origin/CSRF checks remain.

| Path after `/v1/owner/connector/` | Body | Result |
| --- | --- | --- |
| `claim` | `{flow_id, channel_id, offer_handle}` | Atomically bind current session/credential/subject; return `{flow_id, channel_id, return_handle, expires_at_ms}` once. No replacement session may claim an already claimed flow. |
| `list` | `{}` | Latest owned flow summaries, bounded 20, no handles/JWS; enables reload without browser secret storage. |
| `read` | `{flow_id}` | Owned phase, channel_id, original caps, operation_id if present, original binding facts and current effective readiness/retirement. A new session can read history and begin separate compensation, never resume bind mutation. |
| `prepare` | `{flow_id}` | Original session only; compose existing binding preparation with saved reservation and correlation in one transaction. Return operation_id and exact readable descriptor. |
| `activate` | `{flow_id, authorization_id}` | Original session only; compose exact action consumption, stored confirmation, original receipt and `awaiting_resource` lifecycle atomically. |
| `abandon/prepare` | `{flow_id}` | Original flow; current same-owner session plus matching signed never_activated_fenced outcome; create exact AC-017 compensation descriptor. |
| `abandon/complete` | `{flow_id, authorization_id}` | Fresh exact passkey authorization; atomically retire original binding and revoke dependent grants, preserving historical records. |

All wrappers require CSRF, including reads/list for uniformity. Existing action
options/verify supply the actual passkey ceremony. Exact successful activate or
compensation retries read their committed outcome before a second consumption;
historical read does not require the old action/receipt still to be live.

Use private same-connection binding helpers; never nest transaction-owning public
methods. Existing generic/native binding paths must reject connector-tagged
requests so they cannot bypass original-session caps, readiness, correlation or
compensation. Existing action options/verify must consult the same durable
operation-to-flow association. Bind actions require the original bind session/caps;
new compensation actions require their own original current session/operation caps
and exact terminal fact. An expired bind cap is not substituted for the new
compensation cap, nor can the new cap authorize binding activation. Wrappers
still independently enforce those checks at consumption. A connector cannot adopt
an already-existing untagged core request. All association checks occur under the
shared subject mutex and are rechecked in the effect transaction. Existing
untagged native/fixture behavior is unchanged and separately documented.

Retirement preserves request/receipt history. Update both native `get_request`
and web `read_binding` to return the original receipt plus explicit effective
retired state after the exact active slot is removed. They must neither throw
because the historical slot is absent nor describe it as currently active.

MERX owns corresponding same-origin start/pair/sync, actual reserve/confirm password
wrappers, receipt activation and non-authorizing service expiry reconciliation. Those are local
host API decisions. Bind/reserve/confirm/activate mutations retain the original flow/session cap
through their transactions, including activation retries on mutating routes.
Permanent-fact expiry fencing, outcome intake and history are explicitly exempt
from the expired bind cap; they remain authenticated and clock-guarded. ATUM
compensation uses its own new current-session/operation cap. Separate owner
history reads remain possible with a current session. Both host UIs display
the actual stored statement before fresh confirmation.

## Browser channel

MERX creates one random `channel_id` in memory for the flow; ATUM initially sends
only `{version:1,type:"atum-owner-ready"}` after its own login. MERX accepts that
hint only from its retained popup and exact configured origin, then calls start.
Offer message is `{version:1,type:"atum-owner-offer",flow_id,channel_id,offer_handle}`.
ATUM accepts one from its exact opener/origin, pins the pair, and calls claim.
Return message is `{version:1,type:"atum-owner-return",flow_id,channel_id,return_handle}`.
Subsequent hints are `{version:1,type:"atum-owner-status",flow_id,channel_id}`.
All schemas are closed; targetOrigin is literal; messages only trigger bounded
local reads or the explicit pairing call. No message performs owner consent.

Reload/reopen reads owned summaries and resumes only an already paired flow under
the same original local sessions/caps. Reopen uses a new unnamed WindowProxy;
old sources are ignored. Resume is exactly
`{version:1,type:"atum-owner-resume",flow_id,channel_id}`;
the ATUM page must read and validate its own stored flow/channel association before any
status message. A new login cannot resume mutation. Lost unpaired handles require
an explicitly new empty flow. No channel leases, document-nonce persistence,
BroadcastChannel, wildcard origin or URL/storage handles are introduced.

## Terminal outcomes and acceptance

AC-017's exact signed active/never_activated_fenced outcome and separate
historical receipt validator remain required. MERX emits active atomically with
real receipt activation. The trusted service fence requires certainly elapsed
original activation cap (`clock.lower >= D`) and durable never-active history,
under the same stable account/request locks as activation (`clock.upper < D`).
It does not require a new MERX password/session or enabled account. Unknown history
never becomes a negative fact. ATUM compensation is a new exact passkey action in
a current session of the original subject, with its own bounded operation lifetime.
It cannot be inferred from timeout. No second recovery flow is created. Never
change an outcome, reactivate retired history or silently replace a newer binding.

Required implementation sequence: core correlation/lifecycle + vectors and private
PG races; explicit mTLS host/public client; both local owner wrappers/UI; actual
two-site/two-database browser E2E. Include lost open/claim/pair/stage/activation
responses, same-request second-flow rejection, fresh-session takeover rejection,
late activation denial, true historical recovery after restart, fence/activate
race, signed terminal acknowledgement, disabled-account expiry reconciliation, fresh
session compensation, and a fresh successful link.
OAuth grants require the real ready lifecycle. No fixture `ready:true` can close
joint grant/OAuth or G0 acceptance.
